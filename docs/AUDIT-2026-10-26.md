# YiiOffice 全项目技术审计

审计日期：2026-10-26 · 范围：`apps/*`（6 个 app）+ `packages/*`（14 个包）+ 工程化配置
规模：2,532 个 TS/TSX 文件 / 667,062 行；75 个 Playwright spec；约 6,200 个单元测试用例

**一句话结论**：架构分层清晰、OOXML 处理的主干代码质量高于同规模项目，但**工程质量门禁已整体失效**——`lint` OOM、`typecheck` 报错、约 108 个测试用例红、无 CI，且存在 3 处可稳定触发的**静默数据丢失**。

### 1.3 依赖声明错误（会导致跨平台构建失败）

**A. `@typescript/typescript-win32-x64` 被当作运行时依赖**

```jsonc
// apps/docs/package.json
"dependencies": { "@typescript/typescript-win32-x64": "^7.0.2", ... }
```

该包 `os: ["win32"]`、`cpu: ["x64"]`。两处问题：

1. **跨平台阻断**：`dist:mac` / `dist:linux` 在 macOS/Linux 上执行 `npm ci` 会因为显式 dependency 平台不匹配而失败（optional 才会被跳过）。
2. **污染产物**：放在 `dependencies` 会被 electron-builder 打进 asar，多带一份约 100 MB 的编译器二进制。

根 `devDependencies` 也有同一条，但根**没有声明 `typescript` 本身**——所以根目录 `npx tsc` 落到 6.0.3，17 个 workspace 里是 7.0.2：

```
node_modules/typescript                    => 6.0.3     ← 根
apps/docs/node_modules/typescript          => 7.0.2     ← ×17 份独立副本
```

即：同一仓库 23 份 TypeScript 二进制（18 个 workspace + 平台包 2 份 + 根 1 份）。修法：根 `devDependencies` 加 `"typescript": "7.0.2"`，删掉所有子包的 `@typescript/typescript-win32-x64`（平台包由 `typescript` 的 optionalDependencies 自动选择）。

**B. harfbuzzjs 两个大版本并存**

| 位置 | 声明 | 实际 |
| --- | --- | --- |
| `apps/slides` devDeps | `^1.4.0` | 1.6.4（根） |
| `apps/pdf` devDeps | `^0.10.3` | 0.10.3（嵌套） |

`apps/shell/electron-builder.cjs` 打包时**从 `apps/pdf/node_modules/harfbuzzjs` 取 wasm**，而它在 pdf 里是 devDependency——`npm ci --omit=dev` 或 pnpm 严格布局下打包直接失败。同时产物里带两套 wasm（约 2–4 MB），字体子集化与 shaped 结果可能不一致。`apps/pdf/src/main/wasm-path.ts:22-38` 为此写了两条探测路径，是版本分裂的直接证据。

**C. 幽灵依赖（未在 package.json 声明却被 import）**

| 文件 | 未声明的包 |
| --- | --- |
| `apps/markdown/src/renderer/editor/markdownStyleRenderers.ts:3` | `@tiptap/extension-code` |
| `apps/sheets`（9 处） | `@univerjs/ui`、`@univerjs/sheets`、`@univerjs/sheets-ui`、`@univerjs/sheets-formula`、`@univerjs/docs`、`@univerjs/engine-formula` 等 |
| `apps/pdf/src/main/ocr.ts:14`、`ocr-layer.tsx:20` | `@yiioffice/pdf2docx`（用 `../../../../packages/...` 相对路径绕过） |

现在能跑，只因为 npm 的 hoisting 把它们提到了根。换 pnpm/yarn PnP 或依赖树变化，构建立刻断。

**D. 完全未使用的直接依赖**

`apps/slides` 的 `acorn`（全仓 0 引用）。可直接删。

### 2.2 偏离官方文档的

**A. 主进程继承 `DOM` lib，导致 Electron 类型被 DOM 同名接口覆盖**（架构级）

`tsconfig.base.json` 的 `lib: ["ES2022", "DOM"]` 被主进程和前进程共用，于是 `clipboard` 被解析成 DOM 的 `Clipboard` 接口而不是 `Electron.Clipboard`：

```ts
// apps/slides/src/main/element-clipboard.ts:16
clipboard.readBuffer(format)        // error TS2339: Property 'readBuffer' does not exist on type 'Clipboard'
// apps/slides/src/main/slides-main.ts:3370
clipboard.readText().trim()          // error TS2339: Property 'trim' does not exist on type 'Promise<string>'
```

运行时是对的（Electron 有这个 API），但**类型检查在主进程完全失效**——而这 8 处错误一直没人发现，正说明 `typecheck` 没被当门禁跑。修法：`apps/*/tsconfig.main.json` 与 `tsconfig.renderer.json` 分离，主进程用 `lib: ["ES2022"]` + `types: ["node"]`。

**B. 用 Univer 内部路径**

```ts
// apps/sheets/src/renderer/create-univer.ts:11
import { FUniver } from '@univerjs/core/lib/facade'   // 文档写法是 '@univerjs/core/facade'
```

`./lib/*` 在 exports 里可用但属实现细节，1.x 升级时最易断。

**C. 用 pdf.js 的 legacy 构建**

```ts
// apps/pdf/src/renderer/App.tsx:6-8 与 apps/markdown/src/renderer/export/imageExport.ts:16
from 'pdfjs-dist/legacy/build/pdf.mjs'
```

legacy 是为不支持现代语法的旧浏览器准备的（多一套 polyfill、体积更大）。Electron 45 的 Chromium 完全支持 modern 入口 `pdfjs-dist/build/pdf.mjs`。

**D. 偏离"逐字节保真"承诺的 XML 处理**

`saveDocx` 的"文档未变"判定靠手工枚举 27 个 `options.* === undefined`（`packages/docx-engine/src/patch.ts:653`）。新增一个 `SaveOption` 而忘记登记，只传该选项的调用会命中 `return originalBytes`，改动被静默忽略。应改为反向允许列表（只排除 `savedAt`）。

**E. 私改 DI 内部字段**

`apps/sheets/src/renderer/univer-sync.ts:1005` 通过 monkey-patch redi injector 的 `resolutionOngoing` 计数器绕开注入失败。这是当初"双份 core"问题的残留补丁；版本已锁死，补丁只会掩盖真实注册错误。至少应限定 `import.meta.env.DEV`。

## 4. Bug 清单

### P0 — 静默数据丢失 / 数据损坏（可稳定触发）

**1. Markdown 切换同类型文本文件时，编辑器不刷新旧内容，保存会写错文件**

`apps/markdown/src/renderer/source/PlainTextEditor.tsx:128-166`：`EditorState` 只在 `mode` 变化时重建，`initialText` 之后不再读取；`setDoc`（`:180`）全项目零调用；`App.tsx:1024` 也没给组件 `key`。`loadFromPath`（`App.tsx:286-295`）在 source 分支只改 `sourceTextRef.current`。

```
打开 a.txt（源码视图）→ 打开 b.txt → 界面仍是 a.txt 的内容
→ 任意键入触发 onChange → sourceTextRef 变成 a 的内容 → Ctrl+S 覆盖 b.txt
```

修法（一行）：`<PlainTextEditor key={filePath ?? 'none'} …>`，或在 source 分支补 `sourceRef.current?.setDoc(text)`。

**2. DOCX 含嵌套表格的单元格，其自身文字编辑在保存时被丢弃**

`apps/docs/src/renderer/editor/convert.ts:2602-2613`：

```ts
if (cell.nestedTables?.length && originalCell.nestedTables?.length) {
  const nested = ...
  if (nested.some((g) => g !== null)) { changed = true; return { nested } }  // 不带 paras
  return null   // ← 外层段落文本改了也返回 null，静默丢弃
}
```

且 `CellTextsPatch` 的 `paras` 字段（`packages/docx-engine/src/generate.ts:704`）在引擎侧从未被消费——类型承诺了能力，实现没有。用户改完保存，内容回滚，无任何提示。

**3. XLSX 共享字符串把日文/中文注音（`<rPh>`）拼进单元格值**

`packages/xlsx-gateway/src/gateway/xlsx-gateway.ts:3070`：

```ts
[...xml.matchAll(/<si(?:\s[^>]*)?>([\s\S]*?)<\/si>/g)].map((m) =>
  [...m[1].matchAll(/<t(?:\s[^>]*)?>([\s\S]*?)<\/t>/g)]...join(''))
```

`<si><t>東京</t><rPh><t>トウキョウ</t></rPh></si>` 会被读成 `東京トウキョウ`。同一错误在 inlineStr 分支（`:3041`）与 `readHeaderCellText`（`:2101`）各有一份；后者被列名同步调用，一旦回写就把注音写进文件——**不可逆污染**。修法：解析 `<si>` 前先剔除 `<rPh…>…</rPh>` 与 `<phoneticPr>`。

### P1 — 功能失效 / 状态损坏

**4. 关闭窗口时点"取消"，标签管理器被置空**

`apps/shell/src/main/index.ts:1114` 先注册关闭守卫（`window-close-guard.ts:52` 会 `preventDefault()`），`:1116` 又注册了无条件的清理：

```ts
win.on('close', () => {
  if (shellWindow === win) shellWindow = null
  if (tabManager === manager) { tabManager = null; setDockHost(null); publishAllOpenDocuments() }
})
```

Electron 的 `close` 会通知**所有**监听器，`preventDefault` 只阻止默认行为。所以用户"取消关闭"后窗口还在，但 `tabManager` 已是 null → 标签条失联、`ensureTabManager()` 会再建一个窗口。`detached-windows.ts:525` 有同一个模式（取消后 `detached` map 已删，文件路径映射丢失）。

修法：清理移到 `win.on('closed')`，或监听内先判 `event.defaultPrevented`（需保证守卫先注册）。

**5. 任意渲染端可绕过路径授权删除/改名任意文件**

`apps/shell/src/main/index.ts:1520`：

```ts
ipcMain.handle(HOME_CHANNELS.toggleStar, (_event, path) => {
  if (typeof path === 'string') toggleStarredFile(path)   // 不校验路径可见性
})
```

而 `deleteFiles`/`renameFile`/`movePaths` 的授权依据正是"在 root 内 **或被 recents/starred 追踪**"（`file-targets.ts:7`）。于是链路变成：`toggleStar('C:\\任意文件')` → `deleteFiles(['C:\\任意文件'])` → 进回收站。修法：`toggleStar`/`setStarredGroup` 复用 `isUserVisibleFile`。

**6. 68 个 IPC handler 零 `senderFrame` 校验**

全仓 `grep senderFrame` = 0。docs/sheets/slides/pdf/markdown 这些承载用户内容与 AI 输出的渲染端，可以直接调用删除/移动/改名/reveal/PDF 密码提交。`index.ts:2837` 的 `e.sender.id` 校验证明这个模式本可复用，只是没推广。修法：抽 `handleFromShell(channel, fn)` 统一校验 `event.senderFrame.url` 的 scheme+host。

**7. 关闭 docs 标签不销毁 webContents**

`apps/shell/src/main/tab-manager.ts:614` 注释自认"孤儿 webContents 到退出才回收"。每次开关文档泄漏一个完整渲染进程，长时间使用内存单调上涨。

**8. PDF 打开即全量 `getPage`，且全文档从不 `cleanup()`**

`apps/pdf/src/renderer/App.tsx:1106` 为取尺寸遍历每一页建 proxy；`.cleanup()` 只出现在打印的临时文档（`print.ts:109/149`），`PdfPage.tsx` / `PdfThumb.tsx` 渲染完从不释放。pdf.js 6 虽移除了 `proxy.destroy`，但 `page.cleanup()` 仍在且必须调。叠加"标题大纲/表单/注释/搜索"四处各自再遍历一遍全文档（`:25`、`:202`、`:190`、`:178`），同一 PDF 被遍历 3–4 次。

**9. 整份 PDF 经 IPC 一次性搬运，无大小上限**

`apps/pdf/src/main/pdf-main.ts:624` `readFile` 后 `buf.buffer.slice()` 再复制一份，渲染端 `new Uint8Array(data)` 第三份。合并流程有 1 GiB 门槛，单文件打开却没有。

**10. 中文页码 ≥100 显示错误**

`apps/docs/src/renderer/pagination-hf.ts:221`：`n >= 100` 时逐位拼接，第 123 页显示"一二三"而非"一百二十三"。`packages/docx-engine/src/list-markers.ts:114` 的 `toCjkCounting` 已正确实现——同一语义两处实现、行为不一致。
