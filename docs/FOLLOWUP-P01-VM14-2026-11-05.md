## 二、三项改动

### 2.1 调试钩子门禁：`__pageDebug` 有一条功能依赖

原计划是把 `__pageDebug`（`App.tsx:4764`）和 `__docsParseStats`（`parse-off-thread.ts:93`）都改成 `debugHooksEnabled()` 门禁。**读代码后发现这样会打断 CLI 导出**：

`headless-export.ts:22` 的 `pageSliceCount()` 靠 `window.__pageDebug.slices` 判断分页是否稳定，而 `--headless-export` 跑的就是**生产构建**。整体门禁会让该函数恒为 0，`waitForDocumentSettled` 在超时后抛 `pagination produced no pages`，docx→PDF 全挂。

改为**按字段区分**：

- `slices` 无条件发布（功能契约，headless 依赖）
- 其余 20 余个字段（`fastReject`、`colSpecs`、`resumeDiag`、各阶段耗时、`blocks`/`tableRows` 快照）走 `PAGE_DEBUG_DIAG`

```ts
const pageDiag = PAGE_DEBUG_DIAG ? { slices, fastPasses, /* ... */ } : { slices }
;(window as unknown as Record<string, unknown>).__pageDebug = pageDiag
```

两处就地回写（`dbg.fastPasses`、`dbg.frameMs`）也加了同一判断，否则条件展开后的对象会被重新长回诊断字段。

`__docsParseStats` 无功能消费者，直接门禁。

**顺带收益**：诊断对象里的 `colSpecs.map`、`blocks.map`、`tableRows.filter/map`、`secs.map`（含每 section 的 `sectionGeoms` 求值）在生产构建下**不再执行**——这些每次重排都会跑，现在完全省掉。

### 2.2 合并读盘：`hashFile` + `countZipEntries` → `hashAndCount`

原来打开一个工作簿要 open 5 次：`isEncryptedWorkbook`（读头）、`hashFile`（全文）、`excelize.OpenFile`（全文）、`countZipEntries`（中央目录）、`isReadOnly`（写模式 open）。

现在 hash 与 entry 统计共用一个句柄：顺序读完算 SHA-256，再用同一个 `*os.File`（满足 `io.ReaderAt`）交给 `zip.NewReader` 读中央目录，不需要 Seek，也不需要第二次 open。5 次降为 4 次。

**收益必须如实说**：`BenchmarkHashAndCount` 实测两者**耗时持平**（1.14–1.30 ms vs 1.15 ms，差异在噪声内），分配从 74 降到 72 allocs、43543 → 43124 B。原因是 `countZipEntries` 读的中央目录本来就在 page cache 里，省下的只是一次 open/close。

保留这项改动的理由不是速度，是：① Windows 上每次 open 都可能触发安全软件扫描，冷缓存与网络盘场景差异比 benchmark 更大；② 两个函数并成一个，调用点少一处。

> 实现中踩了一个坑并已修正：最初版本手写 1 MiB 缓冲的读循环做取消检查，结果比 `io.Copy` 慢 30% 且每 open 多分配 1 MB。改成 `ctxReader` 包装 `io.Reader`、仍走 `io.Copy` 后恢复持平。

### 2.3 打开超时：`OpenContext`

新增 `Engine.OpenContext(ctx, path, password)`，`Open` / `OpenWithPassword` 委托到它（`context.Background()`），调用方零改动。

bridge 层两处 open 改为带 120 s 截止时间（`workbookOpenTimeout`），超时返回 `ErrOpenTimeout`（`workbook_open_timeout`），经 `codedError` 变成 `open_read_failed: workbook_open_timeout`，前端可识别。

**能力边界（必须写清，否则会被误解为「可以中断任意慢解析」）**：

| 阶段 | 能否被 deadline 中断 |
| --- | --- |
| `isEncryptedWorkbook`（读 8 字节） | 否，但耗时可忽略 |
| `hashAndCount`（全文） | **能**，`ctxReader` 每次 Read 检查 |
| `excelize.OpenFile`（解包解析） | **不能**，无 cancellation hook |
| `sheetMetadata`（流式扫描） | 否，但在阶段边界检查 |

实现是在**阶段边界**检查，并在解析返回后立刻再检查一次：一个在 deadline 之后才解析完的工作簿，不会接着再付元数据扫描的时间。诚实契约是「到点后你不再等」，不是「解析停下了」——超时后底层 goroutine 仍会自然跑完，且**不会注册 session**（已有测试保证）。

## 五、未做与理由

**打开进度上报未做。** 这一项的价值完全取决于是否有消费者：Go 侧加一个 `OnProgress` 回调、bridge 发事件，但前端不显示进度条，等于新增一段无人订阅的死代码——本仓库 P3 清单里正好有「删除仅测试调用的死代码」这一条。

完整落地需要：确定进度在打开遮罩上的呈现方式（百分比？阶段名？）、处理多标签并发打开、超时与进度的交互。这是一次独立的 UI 迭代，不适合塞进本次 Go 侧收尾。

**状态**：超时已提供「不会无限等待」的兜底，进度上报留给前端排期。

## 六、附带发现（未修，供排期）

**`--headless-export` 传相对路径会失败**，退出码 3，错误 `export did not produce a file`；同一命令换绝对路径即成功。渲染本身是成功的（日志中 `MergePdfParts` 已拿到 PDF 数据），失败发生在落盘阶段。

这属于既有可用性问题，与本次改动无关，本次是通过 A/B 实测确认的（绝对路径 `success:true`）。修复方向是 `ValidateHeadlessPaths` 统一 `filepath.Abs` 后再传给渲染器。建议记为 P3。
